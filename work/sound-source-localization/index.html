Sound Source Localization

I went back to my own graduate code and found it never actually computed an answer

Role
Original 2018 master's project at Johns Hopkins, audited and rebuilt solo in 2026
Problem
Estimate a sound source's 3-D position from a microphone array in a reverberant room
Approach
Per-cluster direction-of-arrival, then least-squares ray triangulation
Status
Open source, validated in simulation, live demo hosted
View demo →

My master's project at Johns Hopkins in 2018 tried to locate heart sounds recorded by a microphone array, the front half of an automated murmur detector. I went back to it this year to modernize it and put a demo online. It didn't run.

What I found

The scripts imported modules against a package structure that no longer existed, with no dependency list and no way to install it. Once I fixed the packaging and got it running, I looked at what it was actually producing.

It had never computed a source location. What I'd called an estimate in 2018 was around 500 raw candidate points scattered along a fixed radius sweep, no triangulation step and no clustering step. The method that was supposed to reduce that cloud to a single point built a search structure out of it and then returned nothing. The pipeline emitted an unreduced point cloud and stopped.

Underneath that were four more errors, each quietly corrupting the numbers rather than crashing:

  • The speed of sound was hardcoded to 30 m/s, roughly a tenth of its true value in air. Every direction estimate downstream was scaled against a wrong constant.
  • The angle calculation used a function that can't represent any angle past 90°, so a source below the plane of the array was mathematically unrepresentable. The same function averaged position estimates by dividing by the number of spatial dimensions instead of the number of microphones.
  • Microphone placement dropped the vertical coordinate entirely and never checked generated positions against the room's bounds, so microphones could end up simulated outside the room with no error raised.
  • The reverberation parameters, the entire reason the project targeted a "reverberant room," were accepted as inputs and never passed into the room simulator. The reverberant environment in the project's own title was never actually simulated.

What I rebuilt

The missing piece was a real estimator. Each microphone cluster gives you a bearing, a direction, which is a ray with unknown distance, not a position. Turning several bearings into one position is a geometry problem: find the point that best explains every ray at once. That has a closed-form solution, a linear system solved directly, no sampling grid and no guess-and-check.

Real bearings are noisy, so the rebuilt solver ships three ways to combine them: ordinary least squares, iteratively reweighted least squares with a Huber loss as the default (it down-weights rays whose error is unusually large, typically a reflection mistaken for the direct path), and RANSAC for when a large fraction of the rays are corrupted.

The key design decision

Two constraints came from the array geometry, and both showed up first as wrong numbers.

  • Flat clusters can't tell up from down. A microphone cluster where every mic sits at the same height can't distinguish a source above it from its mirror image below — the inter-microphone delays are identical either way. A flat six-mic array in testing reported 111.08° of colatitude for a true angle of 68.86°; 180° minus 68.86° is 111.14°. It wasn't noisy, it was confidently reporting the reflection. The fix was to give every cluster its own vertical extent, a compact four-microphone tetrahedron instead of a flat polygon, so a single cluster can resolve elevation on its own.
  • Microphones meters apart can't be pooled into one direction estimate. The direction-finding algorithm needs microphone spacing well under half a wavelength, a few centimeters at the frequencies involved. Mixing microphones from clusters meters apart produces phase aliasing and effectively random angles; measured directly, it collapsed the estimate to roughly the average of the cluster locations, about 1.27 m of error. The fix was to compute direction using only each cluster's own tightly-spaced microphones, one ray per cluster, and let triangulation combine the rays. Triangulation only cares about ray geometry, not how far apart the rays start.

Accuracy, including where it fails

I set out to hit sub-centimeter accuracy. The triangulation math gets there. The full acoustic pipeline doesn't, once there's any realistic reverberation in the room. These are measured numbers, not targets:

  • Geometric triangulation, exact bearings: ~10⁻¹³ m, machine precision.
  • Near-anechoic room, real audio and real direction-finding: mean 0.031 m, range 0.010–0.044 m.
  • Lightly furnished room, moderate reverberation: mean 0.121 m, range 0.016–0.183 m.
  • Heavily reverberant room, strong reverberation: mean 1.033 m, range 0.332–1.773 m.

The honest reading: the estimator itself is exact, verified at machine precision by 13 unit tests. The real-audio pipeline reaches single-digit centimeters in the best case and degrades by a factor of thirty in a reverberant room. That's a physical limit of direction-finding from a few-centimeter aperture, not a remaining bug — reflections corrupt the direct-path timing the whole method depends on. Closing that gap in a real reverberant room would take a different approach entirely: a larger array aperture, synchronized time-of-flight hardware, or a direction-finding model trained to tolerate reverberation. That was out of scope, and saying so is more useful than picking a friendlier test room.

I also checked whether the degradation was an artifact of the synthetic signal I'd been testing with, by rerunning the same algorithms against real speech and environmental sound with known simulated ground truth: 135 runs across 3 datasets, 3 reverberation levels, 5 algorithms, and 3 source positions. It wasn't an artifact — reverberation degraded accuracy just as badly on real audio, on every dataset.

Known limits

  • Single source only. Multiple simultaneous sources would need rays grouped by source before triangulating each group; not implemented.
  • The default cluster aperture is a tuned tradeoff at one frequency band and mic count, not a general guarantee.
  • Everything above is one room size, one array layout, and simulated audio only — nothing has been validated against real microphone hardware.
  • The default analysis frequency range is still tuned to the original heart-sound use case and has to be overridden for anything else.

Where it stands

The repo runs end-to-end with 77 passing tests and reports its own accuracy, including the target it misses. A Streamlit demo takes a preset or an uploaded multi-channel recording and shows the estimated position against the true one in 3-D. It's live online and also runs locally through Docker. The code is open for anyone who wants to point it at a different room, a different array, or real hardware, and tell me where the numbers fall apart.
