Feedback Intake Manager: from client markup to team-ready feedback

A human-reviewed AI workflow that turns marked-up PDF proofs into routed feedback teams can act on.

Status
Deployed to production · account-manager pilot scheduled for December 2026
Role
Sole engineer, from discovery through deployment and handover
Build
Six weeks, Sept 25 to Nov 7, 2026

When a pharma client sends back a marked-up proof, someone at Medscape has to read every comment and work out who acts on it before anything can start.

FIM does that first pass. It pulls the annotations out of the PDF, suggests a team for each comment, and flags unclear instructions or missing assets. An account manager reviews every suggestion before exporting an annotated proof and a revision sheet.

I scoped the workflow with the business leads, built the app with AI coding agents, deployed it on WebMD's internal hosting platform, and wrote the handover for the operations team. The December pilot will show how it does in live work.

The problem

Brand-review and medical-legal feedback reaches internal teams untriaged. A proof can carry 100 comments, and a large site can carry 200. Client requests sit next to reviewers' own notes, status updates, and questions nobody can act on yet.

Someone has to sort those comments, find the responsible team, and check that each request says enough to execute. A comment sent to the wrong team costs another handoff. An image swap with no image attached stops work while someone chases the file.

The clearest evidence was already in the files. Staff were writing "For Webservices" and "For Creative" next to comments by hand.

Two questions per comment

FIM asks two things about every comment: who needs to act, and is it ready to hand off?

The first answer is a suggested lane: Compliance, Build edits, Creative edits, Studio for video, or Not routed. The second is a set of flags. A comment might ask for an asset nobody supplied, give an instruction too vague to execute, or turn out to be our own internal note.

Low confidence and Unclear are separate flags on purpose. Low confidence means the model isn't sure which team owns the comment. Unclear means the client hasn't said what they want. The reviewer is fixing a different problem in each case.

The confidence score is the model's own estimate, not a calibrated probability. Suggestions below an adjustable threshold get a Low confidence flag, so they get extra attention in review.

Compliance is a lane, not a user. The Compliance team doesn't work in FIM. Account managers hand Compliance work over to them.

How a review round works

  1. The account manager signs in with a WebMD Google account on the active roster, then uploads a proof or imports it from the submissions tool.
  2. An isolated worker pulls out the annotations, folds duplicates, keeps replies, and flags anything it can't anchor to the page.
  3. Claude Sonnet suggests a lane, flags, a confidence score and a one-line action for each comment.
  4. The account manager reviews the suggestions with the PDF open beside the list. Clicking a comment jumps the viewer to its spot on the page.
  5. Before completing the round, they attest that they checked each lane and every dropped item.
  6. FIM generates an annotated copy of the proof and a revision sheet grouped by team. The client's original comments stay on it, and FIM's decisions sit on top as separate annotations.
  7. The full review exports to a spreadsheet, one row per comment.

Attestations and internal counts stay inside FIM. They never appear in the copy the client receives.

Dropped, not deleted

Some comments need no action. FIM marks those as dropped from the action list, using written rules I worked out with the project lead from historical proofs. A dropped comment stays visible in its own section and can be restored. The account manager confirms the dropped batch before completing the round, and the spreadsheet export records every comment's outcome, dropped ones included.

Deterministic rules run first. A model steps in only when a rule can't read the meaning. New rules run in shadow before they touch a live round. Compliance comments and our own internal notes are never dropped without a person.

Comparing models without touching the review

Claude Sonnet handles routing and the drop rules that need a model. I also tested other models, such as JEV and Haiku 5.5, and built an optional shadow mode that records another model's output next to Sonnet's without changing anything the account manager sees.

What I owned

The routing design came from the people doing the work. I ran demo rounds on real proofs with the project lead, worked through the review flow with the account-manager lead who owns the process, and kept the requirements doc current as decisions changed.

Several of those decisions changed the build:

  • The original routing design was replaced mid-build.
  • The business decided Compliance wouldn't use the app.
  • Each review round would start fresh instead of carrying decisions forward.
  • The output would go to the client.

The fresh-round decision retired a carry-forward feature I'd already built. Because new behavior shipped behind switches that defaulted to off, I could turn the old workflow off while the current one kept running.

Beyond the app itself, I owned access control, the database schema and its 18 migrations, the fixes from a security audit, and the runbook for the operations team that takes FIM over.

Any active reviewer can pick up a job. Operator pages sit behind a separate admin check, and stored proofs are kept for a fixed retention period.

The hard part

The model was the easy part. Most of the work was getting a PDF-heavy app to run on a platform built for something else.

Keeping a bad PDF from taking down the app

The server started with 256 MB of memory. I got that raised, then moved PDF extraction into an isolated worker with its own memory ceiling, timeout and file-size caps. An oversized or stalled proof hits those limits instead of exhausting the main app.

The database allows 15 connections, so heavy jobs run through a queue on the same database and take turns.

Getting it built and connected

The hosting platform ignored the app's own build file. I got a new build image added to the central DevSecOps repo, and ran workarounds until it was approved.

Failures were often silent. Secrets and settings weren't reaching the app and nothing said so, so I built throwaway deployments whose only job was to show which values were missing. Later the server couldn't reach its database, and there were no logs. I wrote diagnostic tools, traced it to a network block, and got it opened through an SRE ticket.

Messy annotations

Client proofs mix margin notes, comment bubbles, highlights, replies and duplicates. FIM has to turn them into one clean list without losing which reply belongs to which comment.

The original PDF library had a known security flaw, so I rebuilt the reader on a patched one. I checked it against two regression proofs with 147 comments between them, plus 13 golden test cases, and its output matched the prototype's.

I also added pre-push checks for the branch names and characters that had broken deployments before.

Security and human control

Client text stays out of git and application logs. Automated test fixtures use scrambled copies of real proofs, and evaluation on real jobs happens only inside the approved environment.

Before the model could touch a real proof, it needed a vendor security review and API approval. I fixed what a security audit found, including adding encrypted database connections, and put a hard spending cap on every test run.

The Compliance stop rule

The pilot has a hard stop. A Compliance comment that FIM drops or sends to the wrong team counts as a miss. One confirmed miss and I turn classification off with the kill switch, and it stays off until the project lead and I have gone through what happened. Account managers keep working in the meantime, setting lanes by hand.

Account-manager review stays after the pilot too. It's part of the product.

Evaluation

I keep three questions apart.

Did the comments come out intact?

The 147-comment regression set and 13 golden cases run on every extraction change.

Did FIM suggest the right team and flags?

Routing is scored offline against a labelled set built with the project lead, and a held-out set of real jobs is still growing. Lanes and flags are scored separately, only on examples with a definite human label. Examples a reviewer marked Not sure are reported on their own, with the share of the set they make up.

Every correction a reviewer makes is stored next to the original suggestion, so pilot corrections become labels for the next evaluation.

Does it help with live work?

That's what the December pilot measures: correction rate, review time and downstream rework. There are no pilot outcomes yet, and offline scores can't tell you how much time FIM saves.

The 30 to 40 incorporation tasks a day behind the project is an estimate. The pilot will measure the real number.

Failures and operations

A proof that goes past the processing limits stops with a clear error. FIM never shows a partial list as if it were complete. If a model call fails, the review screen says so and the account manager sets lanes by hand.

Prometheus and Grafana are provisioned but not connected to FIM yet. Before the pilot I'm adding metrics for stuck jobs, extraction failures, model errors and failed exports, then testing alert delivery and the runbook's recovery steps end to end.

Building with AI coding agents

I was the only engineer, and AI coding agents wrote the code against a written spec. I owned the architecture, the acceptance criteria, the security fixes and every release decision.

Every change had to pass the required checks and come with a written record of what changed and how it was verified. Agents could merge only work I'd approved in advance, and only after a fully green run. I applied the database migrations myself.

When I switched coding tools mid-build, nothing was lost. The next agent picked up from the same spec, handoff notes and verification records.

By the numbers
  • Six weeks of build, active on 34 separate days
  • 18 database migrations, applied by hand in two environments
  • A 147-comment extraction regression set and 13 golden test cases
  • Deployed to production, with a handover runbook for the operations team

Known limits

  • Scanned proofs have no OCR. FIM marks the text as unavailable instead of guessing.
  • Some PDFs carry hidden lookalike annotations that FIM can't yet tell apart from real comments.
  • Email and Word feedback still comes in by hand. Only PDF intake is built.
  • Each comment gets one team. When a comment needs two, the account manager splits it or passes it along.
  • Live accuracy, time saved and downstream effect haven't been measured yet. The pilot starts in December.
